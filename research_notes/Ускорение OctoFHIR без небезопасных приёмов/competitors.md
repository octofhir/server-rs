## 1. Benchmark harness and per-server configuration (fairness)

### Takeaway
All servers share one PostgreSQL 18 container (8 CPU/30 GB) and get 8 CPU/24 GB, but they are not configured equally: Aidbox gets hand-written per-test expression indexes, Medplum indexes only the 16 search parameters the test uses (others are switched off entirely) and gets 4x the DB connection budget, and the search test counts every HTTP response (including 4xx errors) as throughput and never checks result correctness.

### Cited Findings
**Harness**
- PostgreSQL `postgres:18`, limits 8 CPU / 30 GB, one DB per server; `shared_buffers=10GB`, `effective_cache_size=25GB`, `work_mem=10MB`, `random_page_cost=1.1`, `max_parallel_workers_per_gather=4`, `max_wal_size=8GB`, `checkpoint_timeout=15min`, `wal_buffers=256MB`, `max_connections=1000`; `synchronous_commit` left at default (on) — [BENCH@cb5c199:docker-compose.yaml](https://github.com/HealthSamurai/fhir-server-performance-benchmark/blob/cb5c199/docker-compose.yaml), [BENCH@cb5c199:infra/postgres/postgres.conf](https://github.com/HealthSamurai/fhir-server-performance-benchmark/blob/cb5c199/infra/postgres/postgres.conf)
- The `medplum` database alone gets `ALTER DATABASE medplum SET DEFAULT_TRANSACTION_ISOLATION TO 'repeatable read'` — [BENCH@cb5c199:infra/postgres/init/create-database.sql](https://github.com/HealthSamurai/fhir-server-performance-benchmark/blob/cb5c199/infra/postgres/init/create-database.sql)
- Pipeline order: `prewarm.js` → `crud.js` → `import.js` → (since 2026-10-28 no `vacuumdb --analyze`, it was commented out) → `search.js`; each test runs on all servers sequentially (aidbox, hapi, medplum, microsoft, wso2, intersystems) — [BENCH@cb5c199:.drone.yml](https://github.com/HealthSamurai/fhir-server-performance-benchmark/blob/cb5c199/.drone.yml), [commit e6a4941 "Remove vacuumns"](https://github.com/HealthSamurai/fhir-server-performance-benchmark/commit/e6a4941), [BENCH@cb5c199:runner.sh](https://github.com/HealthSamurai/fhir-server-performance-benchmark/blob/cb5c199/runner.sh)

- Search: `constant-vus` 30 VUs, 2 min, `discardResponseBodies: true`, `_count=20`, each iteration walks 24 query groups (string: Patient name/address, Organization name with `""`/`:contains`; date with `eq/lt/gt/ge/le/sa/eb`; token incl. comma-ORs; quantity `value-quantity`, `component-value-quantity`, `combo-value-quantity`; composite `code-value-quantity`, `component-code-value-quantity`, `combo-code-value-quantity`; reference Observation subject/encounter/performer, Encounter subject/participant, MedicationRequest subject/encounter/requester with ids sampled at setup). The only check is `status === 200` — [BENCH@cb5c199:k6/search.js](https://github.com/HealthSamurai/fhir-server-performance-benchmark/blob/cb5c199/k6/search.js), [BENCH@cb5c199:k6/searchConfig.js](https://github.com/HealthSamurai/fhir-server-performance-benchmark/blob/cb5c199/k6/searchConfig.js)
- Headline RPS = `avg_over_time(sum by (fhirimpl)(rate(k6_http_reqs_total{scenario="search"}[1m])))` — i.e. all HTTP requests regardless of status; P99 = `avg_over_time(k6_http_req_duration_p99)` per group — [BENCH@cb5c199:scripts/generate-snapshot.js](https://github.com/HealthSamurai/fhir-server-performance-benchmark/blob/cb5c199/scripts/generate-snapshot.js)

### Inferences
- Fairness asymmetries that matter for interpreting the leaderboard: (a) Aidbox's expression indexes are tailored to the exact parameter set and even to specific test values (partial index on LOINC 8867-4); (b) Medplum disables indexing of every SP outside the test's 16 → much cheaper writes and smaller tables, and turns 10 of the 24 search groups into instant 400s (see §3); (c) Medplum's connection budget is 4× others; (d) "no-cache" header specifically neutralises HAPI's built-in search cache; (e) search correctness is not verified, so a server returning 200 with wrong/empty results or 400 quickly is rewarded.
- Validation is ON for Aidbox (`BOX_FHIR_SCHEMA_VALIDATION=true`) — Aidbox is not winning by skipping validation (at least structurally); Medplum validates on write by default (not changed in config).

### Gaps
- Exact Aidbox `edge` and Medplum `latest` digests used on 2026-10-30 are not recorded in the snapshot; Medplum `latest` is re-tagged on every main commit (Docker Hub shows `latest` updated multiple times per day), so the version is "Medplum main as of ≈2026-10-29 22:23Z (v5.2.12, digest sha256:9a8c26979c90…)" by inference from [Docker Hub tags](https://hub.docker.com/r/medplum/medplum-server/tags).
- Whether HAPI starter defaults `enable_index_missing_fields` to false (making the benchmark's `true` an extra write cost) was not verified from docs.

### Inferences
- With 30 closed-loop VUs, RPS ≈ 30 / mean latency: Aidbox 3392 RPS ⇒ ≈8.8 ms mean; Medplum 3583 ⇒ ≈8.4 ms mean. So means are nearly identical; Aidbox has a far tighter tail, Medplum a flat ~75 ms P99 that looks like per-process event-loop queuing (single-threaded Node, 1 CPU per replica) rather than SQL cost — the P99 doesn't vary by query type, even between queries that hit the DB and ones that are rejected before SQL (§3).
- Aidbox's search is DB-bound (PG pinned at ~98% of its 8 CPUs) because JSONB containment/jsonpath expression predicates are CPU-heavy in Postgres; Medplum's is app-bound and leaves ~85% of PG idle. In a fairer setup (all 24 groups executed) or with more DB data, the relative positions could change either way.

- No per-status (2xx vs 4xx) breakdown or check-failure rate is exported to the snapshot/Grafana panels, so the share of non-200 responses per server could not be read from published data.

## 3. Why Medplum "wins" search (3583 req/s)

### Takeaway
Three things combine: (1) Medplum's schema answers the enabled parameters from dedicated typed columns (hashed-token `UUID[]` with GIN, range columns, lookup tables) so each executed query is cheap for Postgres; (2) its 8 single-CPU Node replicas give 8 independent event loops with 128 DB connections and a Redis cache; and — most importantly for the headline — (3) because only 16 search parameters are enabled, an estimated 10 of the 24 query groups are rejected with HTTP 400 before any SQL, and the benchmark counts those as served requests.

### Cited Findings
- Search-group → SearchParameter mapping vs Medplum's enabled list: enabled = Patient name (`Patient-name`), address (`individual-address`), birthdate (`individual-birthdate`), Organization name, Observation category/code/date/value-quantity, Encounter status/class/date (`clinical-date`), MedicationRequest subject/encounter/requester. NOT enabled = `component-value-quantity`, `combo-value-quantity`, the three composites, Observation subject/encounter/performer, Encounter subject/participant — [BENCH@cb5c199:infra/medplum/config.json](https://github.com/HealthSamurai/fhir-server-performance-benchmark/blob/cb5c199/infra/medplum/config.json) vs [BENCH@cb5c199:k6/searchConfig.js](https://github.com/HealthSamurai/fhir-server-performance-benchmark/blob/cb5c199/k6/searchConfig.js)
- Not-indexed params ⇒ `getSearchParameter()` returns nothing ⇒ `throw new OperationOutcomeError(badRequest(\`Unknown search parameter: ${filter.code}\`))` — [medplum search.ts](https://github.com/medplum/medplum/blob/main/packages/server/src/fhir/search.ts); indexing gate in [structure.ts](https://github.com/medplum/medplum/blob/main/packages/server/src/fhir/structure.ts)
- Health Samurai: Medplum "does not support composite search, so those results are an artifact and are excluded" (in their June write-up) — [performance-at-scale-baseline](https://www.health-samurai.io/articles/performance-at-scale-baseline.md); Medplum's own docs list `composite` as unsupported — [Medplum search architecture](https://www.medplum.com/docs/contributing/search-architecture)
- RPS counts every request (`k6_http_reqs_total`), and k6 only checks `status === 200` — [generate-snapshot.js](https://github.com/HealthSamurai/fhir-server-performance-benchmark/blob/cb5c199/scripts/generate-snapshot.js), [search.js](https://github.com/HealthSamurai/fhir-server-performance-benchmark/blob/cb5c199/k6/search.js)
- Executed searches are cheap: strategy per param type — `date`/`number`/`quantity` → `range-column` (`__<code>` range + `__<code>Sort`); tokens → `token-column` (dedicated `__<code>` UUID[] + `__<code>Text` text[] + sort column, or shared `__sharedTokens`/`__sharedTokensText` for rarely used params); HumanName/Address/Reference/Coding/ConceptMapping → lookup tables; otherwise a plain column (references with a single target type get `singleTargetType`) — [medplum searchparameter.ts](https://github.com/medplum/medplum/blob/main/packages/server/src/fhir/searchparameter.ts)
- Token values are hashed to deterministic UUIDv5 (`v5(value, NIL)`) for `code`, `system|code`, `|code`, `system|`, and searched via `ARRAY_OVERLAPS` (`&&`) on `UUID[]`; `:text`/`:contains` use a case-insensitive regex over a delimiter-joined text array — [medplum token-column.ts](https://github.com/medplum/medplum/blob/main/packages/server/src/fhir/token-column.ts)
- Medplum pads "too unique" UUID[] columns with well-known elements so PG array statistics (MCELEM) give sane selectivity — fix for a planner problem after the token-column switch (4.2/4.3) caused conditional-update regressions — [issue #7310](https://github.com/medplum/medplum/issues/7310), [issue #7539](https://github.com/medplum/medplum/issues/7539), `getPaddingElement` in [token-column.ts](https://github.com/medplum/medplum/blob/main/packages/server/src/fhir/token-column.ts)
- `_total` is computed only when `total=accurate|estimate` is requested; estimate uses `EXPLAIN` row estimates, accurate count only below `accurateCountThreshold` — [medplum search.ts (searchImpl/getCount)](https://github.com/medplum/medplum/blob/main/packages/server/src/fhir/search.ts)
- "Optimized Repository.searchResources (#11124): Avoid calculating links and round trips to the DB for total counts" (merged 2026-10-26, in v5.2.10) — [PR #11124](https://github.com/medplum/medplum/pull/11124)
- Recent targeted partial indexes: Task (`#11178`), Encounter `USING gin ("projectId","status","___tag","__class","__type") … WHERE deleted=false AND status<>'finished'` (`#11186`, merged 2026-10-29) — [PR #11178](https://github.com/medplum/medplum/pull/11178), [PR #11186](https://github.com/medplum/medplum/pull/11186)
- Every Medplum query also carries `deleted=false` and project/compartment filters (`compartments && ARRAY[...]` on `uuid[]`) — [Medplum search architecture](https://www.medplum.com/docs/contributing/search-architecture)

### Inferences
- Roughly 10/24 ≈ 42% of Medplum's measured search requests probably never touch Postgres (strong inference from code + config; not observed directly). This alone explains most of the gap between Medplum's search RPS and its per-query latency, and fits the low PG CPU (≈120%) during its search phase. A like-for-like comparison would either drop those 10 groups for all servers or require 200 responses.
- On the 14 groups Medplum does execute, its per-query SQL is cheap because predicates are on narrow typed columns with GIN/btree/GiST, not on JSONB expressions — the transferable idea for OctoFHIR is "precomputed typed search columns", not Medplum's runtime.
- Turning off unused SPs is a legitimate production lever (Medplum documents it), but it is applied here with knowledge of the exact test parameters.

### Gaps
- Not run locally to confirm 400 responses for e.g. `Observation?subject=Patient/x` with this config (recommended one-line verification).
- No Medplum blog post specifically on the token-column refactor was found; evidence is code + issues.

## 4. Why Aidbox wins CRUD (5297 req/s) and Import (4269 resources/s)

### Takeaway
Aidbox's write path writes a single JSONB row per create (history is written only on update/delete by moving the old version), keeps zero search-index side tables, and in this benchmark has only a handful of expression indexes per table; it runs on a tuned JVM with 16 web threads and a 32-connection pool, and HealthSamurai iterates on the `edge` image against this exact benchmark (custom builds for "fast transaction", "json-optimize", "fast-fhirpath", "tune-validate"). Its import jumped from ~2.7k to ~4.26k res/s on 2026-07-25 with no harness change, i.e. from an engine change.

### Cited Findings
- Storage: one table per resource type (`patient`, …) with `id` (PK), `txid` (bigint from a shared `transaction_id_seq`), `cts`, `ts`, `resource_type`, `status` (enum created/updated/deleted/recreated), `resource jsonb`; `<type>_history` with PK `(id, txid)`; "When you update or delete a resource, Aidbox moves the existing version to the history table before saving the new version" — [Aidbox database schema](https://www.health-samurai.io/docs/aidbox/database/database-schema)
- Default indexes: only primary keys; Aidbox "ships with no search indexes at all" — [Aidbox database schema](https://www.health-samurai.io/docs/aidbox/database/database-schema), [performance-at-scale-baseline](https://www.health-samurai.io/articles/performance-at-scale-baseline.md)
- Search SQL is generated directly over JSONB: token-like `resource @> '{"active":"true"}'::jsonb`; string via `aidbox_text_search(knife_extract_text(resource, '[["name","family"],…]')) ILIKE unaccent('% abc%')`; suggested indexes are GIN on `resource`, `gin_trgm_ops` on the extracted text, btree for ordered access — [Aidbox indexes docs](https://www.health-samurai.io/docs/aidbox/storage-1/indexes); index suggestion RPC (`aidbox.index/suggest-index`, emits `knife_extract_min/max_timestamptz` date indexes) and per-param usage stats in `aidbox_stat.search_param_stats` — [get suggested indexes](https://www.health-samurai.io/docs/aidbox/storage-1/indexes/get-suggested-indexes), [search parameter usage stats](https://www.health-samurai.io/docs/aidbox/deployment-and-maintenance/indexes/search-parameter-usage-stats.md)
- Reference validation: Aidbox rejects references to non-existent targets by default; skipping requires `BOX_FHIR_VALIDATION_SKIP_REFERENCE` + a request header — [Aidbox: skip validation of references](https://www.health-samurai.io/docs/aidbox/modules/profiling-and-validation/skip-validation-of-references-in-resource-using-request-header). The benchmark does not enable that skip — [BENCH@cb5c199:docker-compose.yaml](https://github.com/HealthSamurai/fhir-server-performance-benchmark/blob/cb5c199/docker-compose.yaml)
- Runtime config in benchmark: `BOX_WEB_THREAD=16`, pool 32, `-XX:MaxRAMPercentage=80`, schema validation on, `BOX_FHIR_SEARCH_DEFAULT_PARAMS_TOTAL=none` — [BENCH@cb5c199:docker-compose.yaml](https://github.com/HealthSamurai/fhir-server-performance-benchmark/blob/cb5c199/docker-compose.yaml)
- Vendor iteration on the benchmark: branches pin private Aidbox builds — `fast-transaction` ("Try fast transaction", 2026-03-09, image `aidboxone:git-f135782…`), `json-optimize` (2026-01-20), `tune-validate` (2026-01-26), `fast-fhirpath` (2026-07-06), `java-25` (2025-10), `undertow` ("Try 2604", 2026-07-17), `pg18-async` (`io_method = io_uring`), `alloydb`, `zfs` — `git log`/`git diff origin/main...origin/<branch>` in the local clone ([branches on GitHub](https://github.com/HealthSamurai/fhir-server-performance-benchmark/branches/all))
- Aidbox import history: ≈2.2–3.1k res/s from June to 2026-07-24, then 4262 on 2026-07-25 and ≈4.1–4.7k since, with no harness commit between 2026-07-20 and 07-26; CRUD has been ≈5.2–5.8k since mid-June (dip to ≈2.9k on 2026-06-13..17 and ≈3.8k on 2026-05-08..11, both recovered) — `all/snap_*.json` downloaded from [the GCS bucket listing](https://storage.googleapis.com/storage/v1/b/samurai-public/o?prefix=fhir-server-performance-benchmark/SNAPSHOT_); `git log origin/main --since=2026-07-20 --until=2026-07-26` returns no commits.
- CRUD P99 per op (2026-10-30): Aidbox create 108–134 ms, read 100–126 ms, update 119–140 ms, delete 99–132 ms; Medplum create 634–1024 ms, read 189–575 ms; HAPI ≈210–278 ms; WSO2 create 121–199 ms, read 98–151 ms — [SNAPSHOT_2026-10-30T00:03:50Z.json](https://storage.googleapis.com/samurai-public/fhir-server-performance-benchmark/SNAPSHOT_2026-10-30T00:03:50Z.json)
- PG CPU during CRUD ≈272% for Aidbox vs ≈442% for HAPI; during import ≈272% Aidbox vs ≈440% HAPI and ≈638% WSO2 (computed from the run's [Grafana snapshot](https://grafana.cdr.aidbox.dev/dashboard/snapshot/kX4FlUTLki0a7iSoog4zzvFC20WQRqnV))
- Database size after load (June 28 run): Microsoft 4.24 GB, Aidbox 6.83 GB, Medplum 11.8 GB, HAPI 22.6 GB — [performance-at-scale-baseline](https://www.health-samurai.io/articles/performance-at-scale-baseline.md)

### Inferences
- Per create, Aidbox does 1 heap insert + PK + ~2–4 expression-index inserts on the hot tables; Medplum does main-row upsert (with many search columns + GIN on UUID[] arrays) + `_History` insert + lookup-table rows; HAPI does HFJ_RESOURCE + HFJ_RES_VER + N HFJ_SPIDX_* rows (plus missing-field rows); WSO2 does `resources` + `resource_history` + DELETE/INSERT of `sp_*` rows. Fewer rows/index entries per resource is the dominant reason Aidbox has the lowest DB CPU per write and the highest write throughput. The cost is moved to search time (JSONB predicates, PG saturated in search).
- "No history row on create" is a real write-amplification saving (about half of row writes for insert-only import), at the cost of more work on update (copy old row to history).
- Aidbox's import advantage is consistent with set-based bundle processing (few round trips per bundle), but I found no public doc describing Aidbox's transaction implementation (see Gaps).
- The low and flat P99 (~100–130 ms at 300 VUs) is consistent with a bounded web thread pool (16) + pool 32 and no per-request auth, i.e. queueing in the JVM rather than in Postgres.

### Gaps
- Aidbox is closed source; no public description found of its transaction-bundle write path (batching/COPY/prepared statements), JSON (de)serialisation, or HTTP server (the `undertow` branch name hints at Undertow but is unconfirmed).
- No HealthSamurai article explaining the 2026-07-25 import jump was found.

## 5. Medplum architecture and techniques (in general)

### Takeaway
Medplum = Node.js/TypeScript, per-resource-type Postgres tables with precomputed search columns, hashed-token UUID[] arrays, a handful of lookup tables, a `_History` table written by the app, Redis as a read-through/write-through resource cache, and horizontal scaling by process count.

### Cited Findings
- Write path: `writeToDatabase` runs in one transaction: `writeResource` (`INSERT … mergeOnConflict` of `buildResourceRow`), `writeResourceVersion` (insert into `<Type>_History` with id, versionId, lastUpdated, content), `writeLookupTables`; batch variants (`batchWriteResources`, `batchIndexResources`) exist for bundles — [medplum repo.ts](https://github.com/medplum/medplum/blob/main/packages/server/src/fhir/repo.ts)
- After the write, the resource is put into Redis (`setCacheEntry`; post-commit if inside a transaction); AuditEvents are not cached — [repo.ts `handleStorage`](https://github.com/medplum/medplum/blob/main/packages/server/src/fhir/repo.ts)
- Reads go to Redis first (`getCacheEntry`) and only fall back to `SELECT content, deleted FROM <Type> WHERE id=…`; DB reads served by the writer repopulate the cache — [repo.ts `readResourceImpl`/`readResourceFromDatabase`](https://github.com/medplum/medplum/blob/main/packages/server/src/fhir/repo.ts); reader-replica reads no longer populate the cache ([PR #11161](https://github.com/medplum/medplum/pull/11161)); cache keys normalised to lowercase ids ([PR #11175](https://github.com/medplum/medplum/pull/11175))
- Reference checks on write only if project setting `checkReferencesOnWrite` — [repo.ts](https://github.com/medplum/medplum/blob/main/packages/server/src/fhir/repo.ts)
- Read-only batches can be routed to the reader pool (`readonlyBatchOnReader`, [PR #11142](https://github.com/medplum/medplum/pull/11142)).
- Lookup tables: `AddressTable`, `HumanNameTable` (`HumanName` table with `name/given/family`, `resourceId`, `projectId`; contains uses `ILIKE`), `ReferenceTable`, `CodingTable`, `ConceptMappingTable` — [searchparameter.ts](https://github.com/medplum/medplum/blob/main/packages/server/src/fhir/searchparameter.ts), [lookups/humanname.ts](https://github.com/medplum/medplum/blob/main/packages/server/src/fhir/lookups/humanname.ts); trigram (`gin_trgm_ops`) indexes appear in data migrations v12/v22/v32/v39/v48 ([code search](https://github.com/search?q=repo%3Amedplum%2Fmedplum+gin_trgm_ops+path%3Apackages%2Fserver%2Fsrc%2Fmigrations&type=code))
- A dedicated-vs-shared token column decision list exists to "avoid creating dedicated token columns for search parameters that are rarely used to keep the database schema smaller and have fewer indexes to be maintained" — [searchparameter.ts](https://github.com/medplum/medplum/blob/main/packages/server/src/fhir/searchparameter.ts)
- Medplum's own load test (AWS, 15× Fargate 4 vCPU, PG 16.8 on r6gd.4xlarge, Redis): 20.8k peak req/s authenticated read by id; 6.7k peak (2.4k avg) for create+read+search-by-name mix — [Medplum performance test 2026](https://www.medplum.com/blog/medplum-performance-test-2026)
- Note: Medplum's public "search architecture" doc still describes per-type token lookup tables (`DiagnosticReport_Token`), which the code has since replaced with token columns — [docs](https://www.medplum.com/docs/contributing/search-architecture) vs [token-column.ts](https://github.com/medplum/medplum/blob/main/packages/server/src/fhir/token-column.ts), [issue #7310](https://github.com/medplum/medplum/issues/7310) ("switch to token uuid[] columns with deterministic uuid's" in 4.2/4.3)

### Inferences
- Medplum's CRUD read latency is low relative to its write latency because reads after create/update are Redis hits (the CRUD test reads what it just wrote) — the read P99 (189–575 ms) is still dominated by Node queueing at 300 VUs on 8 single-CPU processes.
- Medplum's import jump (≈850 → ≈3063 res/s on 2026-08-21, right after PR #35) is the cleanest natural experiment for "index fewer search params ⇒ much faster writes" (≈3.6×) — `all/snap_*.json` and [commit 8b71f14](https://github.com/HealthSamurai/fhir-server-performance-benchmark/commit/8b71f14).

### Gaps
- No Medplum source checked for Node cluster mode within one container; the benchmark scales via 8 compose replicas instead.

## 6. WSO2 (Go server in the benchmark) and LinuxForHealth/IBM FHIR

### Takeaway
The "WSO2" entry is a 2026 Go server using one `resources` JSONB table + `resource_history` + per-type `sp_*` index tables (HAPI-like normalization) with no GIN on the document; it is #2 on CRUD/Import but its reference searches are slow (P99 up to 1.28 s) and it fails closed on composite searches. LinuxForHealth (IBM) is a different, Java server with a normalized parameter-table schema.

### Cited Findings
- WSO2 Go: single `resources` table keyed `(tenant_id, resource_type, fhir_id)` with `resource_json` JSONB; "No GIN index on resource_json … would cost roughly 2.4× on write throughput"; append-only history; soft delete with partial index `WHERE is_deleted = FALSE`; `sp_string` (`value_exact`, `value_lower`, `text_pattern_ops`), `sp_token` (system,code + code-only partial index), `sp_date` (partial dates expanded to `[value_low, value_high]` at write), `sp_quantity` (raw + UCUM-canonical), `sp_reference`; on update `sp_*` rows are DELETE+INSERT; composite/unsupported-but-known params return an error ("fail closed"); unknown params use a heuristic instead of rejection — [wso2/fhir-server DESIGN.md](https://github.com/wso2/fhir-server/blob/main/DESIGN.md)
- WSO2 perf notes: narrow `(tenant_id, resource_id, resource_type)` source indexes on `sp_*`, dropped redundant indexes, `SET STATISTICS 1000` on high-cardinality columns, `autovacuum_vacuum_scale_factor = 0.02` because throughput degraded after ~500 s under default autovacuum — [DESIGN.md §15](https://github.com/wso2/fhir-server/blob/main/DESIGN.md)
- WSO2 search RPS fell from ≈3.6–4.3k (Sep–mid Oct) to ≈1.9–2.3k from 2026-10-28; reference P99 Observation 395 ms (2026-09-30) → 1200–1283 ms (2026-10-29/30) — `all/snap_*.json` from the [bucket](https://storage.googleapis.com/storage/v1/b/samurai-public/o?prefix=fhir-server-performance-benchmark/SNAPSHOT_)
- LinuxForHealth FHIR schema: `logical_resources` (+ per-type `xx_logical_resources`), `xx_resources` (versions, soft delete `IS_DELETED` denormalized into `xx_logical_resources` "as a performance optimization"), `logical_resource_ident` for reference targets and row locking, `xx_str_values`, `xx_date_values`, `xx_ref_values`, `xx_resource_token_refs` mapping to normalized `common_token_values`; Postgres ingestion via `add_any_resource` stored procedures; experimental Citus distribution — [LinuxForHealth SchemaDesign.md](https://github.com/LinuxForHealth/FHIR/blob/main/fhir-persistence-schema/docs/SchemaDesign.md); repo last pushed 2024-04-18 ([repo](https://github.com/LinuxForHealth/FHIR))

### Inferences
- WSO2's composite group (P99 ~75 ms) likely returns fast errors, similar to Medplum's disabled params (composite is "fail closed" per DESIGN.md); its RPS is therefore also inflated somewhat.
- The 2026-10-28 regression coincides with removal of the post-import `vacuumdb --analyze` (`e6a4941`) and/or a new WSO2 `latest` image; normalized `sp_reference` joins are sensitive to stale planner statistics after a bulk load. Unverified.

### Gaps
- LinuxForHealth JDBC batching, caching and query generation details were not researched further (not in this benchmark).

## 7. HAPI FHIR JPA

### Takeaway
HAPI's normalized HFJ_SPIDX_* tables with 64-bit hash columns make each predicate an indexed equality on a long, but every resource write fans out into many index rows (largest DB: 22.6 GB vs Aidbox 6.83 GB), and searches go through the HFJ_SEARCH paging machinery; in the benchmark its result cache is disabled and missing-field indexing is enabled.

### Cited Findings
- Hash columns use "MurmurHash3_x64_128 … keeping only the first 64 bits"; `HASH_IDENTITY` = hash(SP_NAME, RES_TYPE); token `HASH_VALUE`, `HASH_SYS_AND_VALUE`, `HASH_SYS`; string search = `HASH_IDENTITY` + `LIKE` on `SP_VALUE_NORMALIZED`, `:exact` uses `HASH_EXACT`; date ordinals `YYYYMMDD`; quantity `HASH_IDENTITY_AND_UNITS`, `HASH_IDENTITY_SYS_UNITS`; HFJ_RES_VER may store JSONC (compressed JSON); HFJ_RESOURCE `HASH_SHA256` detects no-op writes — [HAPI JPA schema](https://hapifhir.io/hapi-fhir/docs/server_jpa/schema.html)
- Performance knobs: `setIndexStorageOptimized(true)` stops writing `SP_NAME`/`RES_TYPE` into HFJ_SPIDX rows; `X-Upsert-Extistence-Check: disabled` skips SELECT before client-id upserts; suppress `:text` token indexing; disabling delete skips some reference checks on create; history `COUNT_CACHED` default; ID lists >800 bound as one JSON param — [HAPI JPA performance](https://hapifhir.io/hapi-fhir/docs/server_jpa/performance.html)
- Search cache default 60 s, bypassed by `Cache-Control: no-cache`; `no-store, max-results=N` disables paging for the request — [HAPI JPA configuration](https://hapifhir.io/hapi-fhir/docs/server_jpa/configuration.html)
- Benchmark: HAPI composite P99 682 ms; other families 75–106 ms; search 1013 RPS; PG ≈379–440% CPU during HAPI phases — [SNAPSHOT_2026-10-30](https://storage.googleapis.com/samurai-public/fhir-server-performance-benchmark/SNAPSHOT_2026-10-30T00:03:50Z.json), [Grafana snapshot](https://grafana.cdr.aidbox.dev/dashboard/snapshot/kX4FlUTLki0a7iSoog4zzvFC20WQRqnV)

### Inferences
- In the search test HAPI pays for both the normalized joins and the HFJ_SEARCH bookkeeping per request (the no-cache header prevents reuse but, as far as I know, does not avoid paging persistence unless `no-store` is sent). The benchmark could likely gain by sending `Cache-Control: no-store, max-results=20` for HAPI — docs say this "can cause a noticeable performance improvement".

### Gaps
- HAPI defaults for `enforce_referential_integrity_on_write` and `enable_index_missing_fields` in the starter were not confirmed from docs in this session; HAPI bulk import ($import / mass ingestion mode) details not gathered.

## 8. Microsoft FHIR server (SQL Server)

### Takeaway
MS FHIR stores resources in a `Resource` table and every search parameter type in its own table (including composites), writing all of them through one stored procedure with table-valued parameters; it indexes all SPs by default, which makes writes slow (710 CRUD RPS, 623 res/s import) and quantity/composite searches very slow in this benchmark.

### Cited Findings
- `dbo.MergeResources` takes TVPs `@Resources`, `@ReferenceSearchParams`, `@TokenSearchParams`, `@TokenTexts`, `@StringSearchParams`, `@UriSearchParams`, `@NumberSearchParams`, `@QuantitySearchParams`, `@DateTimeSearchParms`, `@VectorSearchParams` and six composite TVPs (`ReferenceTokenComposite…`, `TokenTokenComposite…`, `TokenDateTimeComposite…`, `TokenQuantityComposite…`, `TokenStringComposite…`, `TokenNumberNumberComposite…`); supports single-version put, history-preserving put, and store-to-store copy with surrogate ids — [MergeResources.sql](https://github.com/microsoft/fhir-server/blob/main/src/Microsoft.Health.Fhir.SqlServer/Features/Schema/Sql/Sprocs/MergeResources.sql); related sprocs `MergeResourcesBeginTransaction`, `MergeResourcesCommitTransaction`, `MergeResourcesAdvanceTransactionVisibility` — [Sprocs dir](https://github.com/microsoft/fhir-server/tree/main/src/Microsoft.Health.Fhir.SqlServer/Features/Schema/Sql/Sprocs)
- Bundles are processed sequentially by default; `x-bundle-processing-logic: parallel` enables parallel entries; >100 concurrent bundle requests "may lead to negative scaling" — [Azure FHIR best practices](https://learn.microsoft.com/en-us/azure/healthcare-apis/fhir/fhir-best-practices), [REST API capabilities](https://learn.microsoft.com/en-us/azure/healthcare-apis/fhir/rest-api-capabilities)
- `$import` (NDJSON) is the high-throughput path: initial mode blocks API writes; optimal files ≥50 MB / ≥20K resources; runs on distributed infrastructure splitting files into data units processed in parallel — [Import FHIR data](https://learn.microsoft.com/en-us/azure/healthcare-apis/fhir/import-data); Microsoft notes that selecting a subset of search parameters "can have significant positive performance impact" (per search summary of a Microsoft blog; not opened directly).
- Benchmark: Patient create P99 5365 ms; composite search P99 2975 ms, quantity 2577 ms — [SNAPSHOT_2026-10-30](https://storage.googleapis.com/samurai-public/fhir-server-performance-benchmark/SNAPSHOT_2026-10-30T00:03:50Z.json)

### Inferences
- MS FHIR is the clearest example of the opposite trade-off to Aidbox: index everything eagerly (smallest DB thanks to compression/normalization, 4.24 GB) and pay on every write.

### Gaps
- Did not check MS FHIR's search SQL generation (CTE chains) or caching.

## 9. InterSystems IRIS for Health

### Takeaway
IRIS is slowest because of harness constraints (Community Edition, 16-request concurrency cap, per-request Basic auth, synchronous journal commit) plus its generated search tables needing statistics (TuneTable) that the pipeline stopped gathering on 2026-10-28.

### Cited Findings
- Community Edition caps at 20 cores and 8 license units; Web Gateway by default spawns an IRIS process per in-flight request (~375 under 300 VUs) "thrashing … at half the throughput or less", so the harness caps concurrency at 16 — [docker-compose.yaml comments](https://github.com/HealthSamurai/fhir-server-performance-benchmark/blob/cb5c199/docker-compose.yaml), [httpd-local.conf](https://github.com/HealthSamurai/fhir-server-performance-benchmark/blob/cb5c199/infra/intersystems/httpd-local.conf)
- `SynchCommit=1` set deliberately (IRIS default 0 would return before journal flush) — [merge.cpf](https://github.com/HealthSamurai/fhir-server-performance-benchmark/blob/cb5c199/infra/intersystems/merge.cpf)
- Default `MaxSearchResults=1000` returns 413 for larger matches; raised to 10M — [fhir-server.sh](https://github.com/HealthSamurai/fhir-server-performance-benchmark/blob/cb5c199/infra/intersystems/fhir-server.sh)
- InterSystems recommends running Tune Table on the generated search tables and applying default selectivities (`SetDefaultSearchTableSelectivities()`) to improve search plans — [IRIS FHIR server maintenance docs](https://docs.intersystems.com/irisforhealthlatest/csp/docbook/DocBook.UI.Page.cls?KEY=HXFHIRADM_server_maintain); the benchmark's `gather-stats.sh` step was commented out on 2026-10-28 — [commit e6a4941](https://github.com/HealthSamurai/fhir-server-performance-benchmark/commit/e6a4941)
- Results: CRUD 504 RPS, import 1090 res/s, search 507 RPS, date-Observation P99 16.5 s — [SNAPSHOT_2026-10-30](https://storage.googleapis.com/samurai-public/fhir-server-performance-benchmark/SNAPSHOT_2026-10-30T00:03:50Z.json)

### Inferences
- With only 16 concurrent server processes and multi-second searches, IRIS's search RPS is bounded by queueing; it is not a meaningful engine-to-engine comparison.

## 10. Cloud services (Google Cloud Healthcare API, Azure Health Data Services, AWS HealthLake)

### Takeaway
None of the managed services is in the benchmark; what is public are quotas, not architecture-level performance numbers.

### Cited Findings

- Managed services trade per-request latency for elastic scale; their published quotas (e.g. HealthLake 100 searches/s) are below single-node OSS servers in this benchmark, so they are not useful performance references for OctoFHIR.

### Gaps
- I found no primary source confirming that Google's FHIR store runs on Spanner or describing HealthLake's indexing internals.

## 11. Prior runs, vendor tuning, and what changed over time

### Takeaway
The benchmark is re-run nightly; numbers are stable for Aidbox and HAPI, while Medplum's improved in two steps (2026-08-21 after its own config PR, and 2026-10-30 unexplained), and WSO2's search regressed from 2026-10-28.

### Cited Findings
- Aidbox CRUD ≈5.2–5.8k since mid-June 2026; Import ≈4.1–4.7k since 2026-07-25; Search ≈3.0–3.6k since search tests started on 2026-06-19. HAPI CRUD ≈2.9–3.2k, import ≈2.0–2.4k, search ≈0.9–1.1k throughout — `all/snap_*.json` (151 snapshots, 2026-05-01..2026-10-30) from the [bucket listing](https://storage.googleapis.com/storage/v1/b/samurai-public/o?prefix=fhir-server-performance-benchmark/SNAPSHOT_)
