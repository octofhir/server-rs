# Performance-focused dependency audit and measurement methodology for OctoFHIR

Method note: "ours" versions come from `Cargo.lock` (resolved), requirement strings from `Cargo.toml` files. "Latest" versions come from the crates.io JSON API (`https://crates.io/api/v1/crates/<name>`, field `max_stable_version`), queried on 2026-10-30. Duplicate versions come from `cargo tree -d --offline -e normal -p octofhir-server` on macOS (host target, so Linux-only deps such as `openssl` under `native-tls` are not shown). Changelogs were read from the upstream repositories. Nothing in the repo was modified, and no `cargo update` or builds were run.

## Q1: For each key dependency, which versions came out after ours, what changed for performance, what breaks, how risky is the upgrade, and in what order?

### Takeaway
The hot path is already on the latest releases: sqlx 0.9.0, tokio 1.54.1, axum 0.8.9, tower 0.5.3, serde_json 1.0.154, tracing 0.1.44, tracing-subscriber 0.3.23, regex 1.13.1, mimalloc 0.1.52 and chrono 0.4.45. Upgrades will therefore not bring large speedups. The useful work is: (a) semver-compatible patch bumps (hyper 1.12, uuid 1.29, time 0.3.55, rustls 0.23.46, moka 0.12.16, reqwest 0.13.5, arc-swap 1.9.3); (b) removing duplicate crates, chiefly tower-http 0.6/0.7, reqwest 0.12/0.13 and octofhir-ucum 0.5/0.8; (c) changing the JWT crypto backend from `rust_crypto` to `aws_lc_rs`, since aws-lc-rs is already compiled in via rustls; (d) breaking upgrades with indirect value only: rquickjs 0.11→0.14, which fixes a deadlock under the `parallel` feature we use, opentelemetry 0.31→0.33 and jsonwebtoken 10→11.

### Inferences
- Wall-clock gains from upgrades alone are likely small, because the request path (tokio, hyper, axum, sqlx, serde_json, mimalloc) is already current. Performance work should target application code and SQL, not dependency bumps.
- The `rust_crypto` JWT backend probably makes RS256 verification on every authenticated request slower than aws-lc-rs would be. However, the benchmark runs with `OCTOFHIR__AUTH__POLICY__ANONYMOUS_ACCESS: 'true'`, so it may not exercise token verification at all. Check this with a criterion bench before claiming a gain.
- Compiling both `ring` and `aws-lc-rs` adds build time and binary size. Pinning one rustls provider across reqwest/lettre/metrics-exporter could be possible, but I have not verified the exact feature flags.

### Gaps
- No published benchmark numbers were found that compare jsonwebtoken `rust_crypto` vs `aws_lc_rs` for RS256/ES384 verify.
- Not reviewed: changelogs for uuid (raw CHANGELOG URL 404), time, hyper-util and arc-swap; tokio 1.54.0's long changelog (about 160 lines) beyond the grep for perf keywords; serde_json `arbitrary_precision`/`raw_value` trade-offs.
- Duplicate analysis covered the macOS host only; Linux-only deps (openssl-sys under native-tls) were not examined.
- I did not check whether the external path deps (fhirpath-rs, fhirschema, canonical-manager) have newer releases.

## Q2: How do we reproduce the HealthSamurai benchmark locally, profile the server, and gate performance regressions in CI?

### Takeaway
The benchmark is a docker-compose stack with an 8-CPU/20 GB OctoFHIR container, an 8-CPU/30 GB Postgres 18 with `pg_stat_statements`, and k6 in a container on the same host with no CPU limit. It runs prewarm → CRUD (300 VUs × 4 m) → import (Synthea `bulk_1k`) → `vacuumdb --analyze` → search (30 VUs × 2 m). A laptop reproduction should keep the server/DB CPU ratio but scale both down, pin cpusets so they don't overlap, and put k6 on separate cores or a separate host. For CI, use deterministic instruction-count benches (gungraun, or CodSpeed `simulation` mode as ruff does) for per-PR gates. Run wall-clock k6 load with thresholds nightly, comparing against a baseline SHA on the same hardware as Vector does.

### Cited findings — the HealthSamurai benchmark (local clone, branch `octofhir`, read via `git show`)
- The CI is Drone, pinned to node `hz-cdr`, using docker-in-docker with host caches for images/overlay and a host volume `/var/data/storage/pgdata/perf-test-search` mounted as `search-dataset` — `git show octofhir:.drone.yml` (lines 1-40) in `/Users/alexanderstreltsov/work/octofhir/fhir-server-performance-benchmark`.
- The `configure` step writes a compose override that disables every server except `octofhir aidbox` (hapi, medplum, redis, mssql, microsoft, wso2, intersystems → `profiles: [donotstart]`). It mounts `infra/postgres/postgres.conf` and adds Prometheus `remote_write` with `commit`/`branch`/`runid` labels — `.drone.yml` configure step.
- The test sequence, from `.drone.yml` `test` step (`SERVERS: octofhir aidbox`):
  1. `./runner.sh bootstrap`
  2. `./runner.sh -t /k6/prewarm.js`
  3. `./runner.sh -t /k6/crud.js`
  4. `./runner.sh -t /k6/import.js`
  5. `docker exec perf-postgres vacuumdb --analyze -j 50 -U postgres --all`
  6. `./runner.sh -t /k6/search.js`
  7. `docker compose down -v`

### Cited findings — profiling tools
- **pprof-rs**: an in-process sampling profiler. `ProfilerGuardBuilder::default().frequency(1000).blocklist(&["libc","libgcc","pthread","vdso"])`; features `flamegraph`, `prost-codec`/`protobuf-codec` (pprof protobuf output); the `frame-pointer` feature is "only available for nightly" — [pprof-rs README](https://github.com/tikv/pprof-rs/blob/master/README.md). It fits behind an admin-only `/debug/pprof` endpoint for continuous or on-demand profiling inside the benchmark container, where `perf` may be unavailable.
- **tokio-console**: requires the `tokio_unstable` cfg (`RUSTFLAGS="--cfg tokio_unstable" cargo build` or `rustflags = ["--cfg","tokio_unstable"]` in `.cargo/config.toml`) and the `console-subscriber` crate — [console-subscriber README](https://github.com/tokio-rs/console/blob/main/console-subscriber/README.md). Use it to find tasks that block the executor and to see poll times. It needs a separate profiling build and should not run in benchmark images.
- **cargo-flamegraph / samply**: the repo already has `just flame` (cargo-flamegraph) and a `profiling` Cargo profile annotated "needed for samply name resolution" (Cargo.toml:135-151). Tool homes: [flamegraph-rs](https://github.com/flamegraph-rs/flamegraph), [samply](https://github.com/mstange/samply). samply runs natively on macOS, while `perf` needs Linux.
- **pg_wait_sampling**: must be in `shared_preload_libraries`, and when loaded together with `pg_stat_statements` it must be placed *after* it so queryIds match. It provides a wait-event history kept "as in-memory ring buffer" and a cumulative profile (`pg_wait_sampling_profile`) that a client can periodically dump and reset — [pg_wait_sampling README](https://github.com/postgrespro/pg_wait_sampling/blob/master/README.md). This would mean adding it to the benchmark's `postgres.conf` (which today has only `pg_stat_statements`) in a local override, and the image would need the extension installed. Without an extension, sample `SELECT wait_event_type, wait_event, count(*) FROM pg_stat_activity WHERE state='active' GROUP BY 1,2` every 100 ms ([pg_stat_activity docs](https://www.postgresql.org/docs/current/monitoring-stats.html#MONITORING-PG-STAT-ACTIVITY-VIEW)).
- **pg_stat_statements** is already preloaded in the benchmark Postgres (`postgres.conf`). Reset it before each k6 phase with `pg_stat_statements_reset()` and snapshot the top queries by `total_exec_time` afterwards ([docs](https://www.postgresql.org/docs/current/pgstatstatements.html)). **auto_explain** (`auto_explain.log_min_duration`, `log_analyze`, `log_buffers`) catches slow plans under real load ([docs](https://www.postgresql.org/docs/current/auto-explain.html)). **pg_stat_io** gives per-backend-type I/O counters ([docs](https://www.postgresql.org/docs/current/monitoring-stats.html#MONITORING-PG-STAT-IO-VIEW)). MEMORY notes that `_debug=search-explain-analyze` exists in-server for per-query EXPLAIN.

### Cited findings — CI regression gates used by comparable projects
- **rustc-perf** compares test results by metric (for example instruction count). A comparison counts as "significant" above a computed significance threshold and as "relevant" only if it is significant *and* of at least small magnitude — [rustc-perf glossary](https://github.com/rust-lang/rustc-perf/blob/master/docs/glossary.md), [comparison-analysis](https://github.com/rust-lang/rustc-perf/blob/master/docs/comparison-analysis.md#what-makes-a-test-result-significant).
- **ruff (Astral)**: CI runs `cargo codspeed build -m simulation -m memory ... --profile profiling -p ruff_benchmark --bench formatter --bench lexer --bench linter --bench parser`, then `CodSpeedHQ/action@... # v5.2.1` with `mode: "simulation,memory"` and `cargo codspeed run` — [ruff ci.yaml](https://github.com/astral-sh/ruff/blob/main/.github/workflows/ci.yaml) (around lines 1256-1374). CodSpeed's Rust integration supports divan (listed as recommended), criterion.rs and bencher (libtest) through compatibility layers, plus a `cargo-codspeed` subcommand — [codspeed-rust reference](https://codspeed.io/docs/reference/codspeed-rust).
- **Gungraun** (iai-callgrind renamed: "With the `0.17.0` version the project was renamed to `Gungraun`") runs benchmarks under Valgrind tools (Callgrind, Cachegrind, DHAT) and Linux perf. It reports instruction counts and "Estimated Cycles", runs each benchmark once, and is "perfectly suited to run in environments like a CI". It does not run on Windows. Soft limits are percentage differences vs the old run, suffixed with `%`; hard limits cap absolute metrics. Relevant options are `--callgrind-limits`, `--regression-fail-fast` / `GUNGRAUN_REGRESSION_FAIL_FAST`, `--save-baseline`, `--baseline`. It is supported by Bencher — [gungraun README](https://github.com/gungraun/gungraun), [gungraun CHANGELOG](https://github.com/gungraun/gungraun/blob/main/CHANGELOG.md). Latest is gungraun 0.20.0 (2026-09-26); iai-callgrind stopped at 0.16.1 (2025-07-30) — [crates.io](https://crates.io/crates/gungraun).
- **Bencher.dev** threshold models include Static, Percentage, z-score, t-test, Log Normal, Interquartile Range (IQR) and Delta IQR tests with upper/lower boundaries — [Bencher thresholds](https://bencher.dev/docs/explanation/thresholds/).
- **Vector (Datadog)** runs a "Regression Detection Suite" weekly or on demand (`/ci-run-regression` PR comment). It performs "relative evaluations of the baseline SHA and comparison SHA" (default baseline: master 7 days ago), checking whether "throughput performance has degraded or become more variable". It uses the SMP tool and the `lading` load generator (`lading: version: 0.33.0`) with `SMP_WARMUP_SECONDS: 70` and `SMP_REPLICAS: 100` — [Vector regression.yml](https://github.com/vectordotdev/vector/blob/master/.github/workflows/regression.yml), [regression/config.yaml](https://github.com/vectordotdev/vector/blob/master/regression/config.yaml).
- **k6 thresholds** make k6 exit with a non-zero exit code when they fail. `abortOnFail: true` (optionally with `delayAbortEval: '10s'`) stops the run as soon as a threshold fails — [k6 thresholds docs](https://grafana.com/docs/k6/latest/using-k6/thresholds/).
- I found no source for **divan** beyond crates.io: latest 0.1.21 (2025-04-10), meaning no release in about 18 months — [crates.io](https://crates.io/crates/divan). Criterion 0.8.2 is current.

### Inferences (proposed methodology)
- **Scaled-down laptop reproduction.** Keep the 1:1 server:DB CPU ratio from the benchmark (8:8) but scale it, e.g. `--cpuset-cpus` 0-3 for octofhir, 4-7 for Postgres, and run k6 on the remaining cores or on a second machine. k6 is unconstrained in the original, so on a laptop it competes for CPU. Scale VUs proportionally (300 VUs/8 cores → roughly 150 VUs/4 cores) and `shared_buffers` to about 25% of the RAM given to the Postgres container. Copy the octofhir env block verbatim from the compose file, including `INDEXED_PARAMS`, `COMPOSITE_INDEXES` and `CHECK_TARGET_PROFILE=true`. Otherwise the search numbers are not comparable. `FETCH_EXTERNAL_REFERENCES=true` plus the external terminology URL inject network variance, so record whether they were on.
- On macOS, Docker containers run inside a Linux VM, so `--cpus`/`--cpuset` bound the VM's vCPUs, not physical cores. For trustworthy absolute numbers, use a Linux box. Use the laptop for relative A/B runs: same machine, alternating baseline/candidate, at least 3 runs each.
- **Phase discipline** (mirrors Drone): prewarm, then CRUD, then import, then `vacuumdb --analyze`, then search. Before each phase, call `pg_stat_statements_reset()`. After each phase, snapshot `pg_stat_statements`, `pg_stat_io` and the wait-event samples. Keep the `runid` tag so Grafana/Prometheus panels line up.
- **Profiling ladder:** use the samply/flamegraph `profiling` build for CPU hot spots; tokio-console in a `tokio_unstable` build for scheduler stalls; pg_stat_statements + auto_explain + wait sampling for DB time. pprof-rs is the only option that works inside the unmodified benchmark container without `perf` privileges.
- **CI gates:**
  - (a) Per PR: gungraun or CodSpeed-simulation instruction-count benches over pure-Rust hot paths, such as search query compile (already in `date_search.rs`), FHIR JSON parse/serialize, validation, and policy evaluation (`quickjs_bench.rs`), with soft limits of roughly 2–5%.
  - (b) Nightly: wall-clock k6 with thresholds on a fixed self-hosted runner, comparing against a stored baseline. Use Bencher t-test/IQR thresholds, or follow Vector and run baseline and candidate SHAs back-to-back on the same host.
  - (c) Align `benchmark.yml` to postgres:18 and to the HealthSamurai k6 scripts and env so nightly numbers predict the public benchmark.
