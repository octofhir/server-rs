# Ресерч: двунаправленный конвертер C-CDA ⇄ FHIR на декларативных картах

Дата: 2026-11-04. Цель: C-CDA ⇄ FHIR R4 (затем R5) на декларативном описании, а не хардкодом. Код не пишется до выбора варианта.

## Решение (кратко)

**Рекомендация: вариант A.** Это FML через наш fml-rs, логические модели CDA от HL7 и чтение/запись XML в fml-rs как общий слой. Сверху — дисциплина двунаправленности: парные карты на каждый домен, общие карты типов данных и обязательный round-trip-прогон по корпусу. Свой DSL (вариант B) не делать.

**Почему A.**
1. **HL7 сам идёт к FML.** На ветке `fsh` C-CDA on FHIR лежит черновик `design-structuremap.md` от 2026-07-20. Он предлагает StructureMap/FML как исполняемую форму карт, `hl7.cda.uv.core` как исходную модель и `translate()` по ConceptMap [A2]. Свой DSL нас от этого отрезает.
2. **Модели готовы и открыты.** `hl7.cda.uv.core` 2.0.3-sd и `hl7.cda.us.ccda` 5.0.0 распространяются под CC0. В них 139 и 229 StructureDefinition. XML-представление описано расширениями tools (`xml-namespace`, `xml-name`, `xml-choice-group`, `representation` = xmlAttr/typeAttr/xmlText/cdaText) [A1]. Читать XML «по модели» — механическая задача, а не дизайн языка.
3. **Основная работа одинакова для A и B.** Это слой XML и типов данных CDA (xsi:type, IVL_TS, PQ, ED, TS с точностью и зоной, nullFlavor) и маршрутизация по templateId. На этом слое ошибаются все открытые конвертеры [B3]. Свой DSL эту работу не убирает, а добавляет язык, парсер, проверку типов, движок, документацию и инструменты.
4. **У нас уже есть движок FML с паритетом.** fml-rs: 1643/1643 карт совпадают с эталонным компилятором HL7. Есть проверка типов по FHIR Schema, трассировка `$transform?debug` и лимиты для пользовательских карт. В A эти вложения работают на CDA, в B их пришлось бы повторить.
5. **Обратимость в B — иллюзия.** HL7 пишет прямо: двунаправленное автоматическое преобразование возможно в узких случаях, но «не без потерь» [A2]. Нарратив, nullFlavor (UNK и NI оба → `unknown`), контекстная проводимость автора → Provenance — односторонние по природе. «Линзы» дали бы обратимость только там, где она и так тривиальна. Все найденные открытые двунаправленные инструменты держат два независимых пути [B5].

**Объём (один разработчик).**
- MVP: CDA→FHIR R4 для заголовка и 7 доменов с консенсусными таблицами HL7, метрики по корпусу. Около **2,5–3 месяцев**.
- Полный двунаправленный охват 12 доменов CF и 7 FC с round-trip: около **5–6 месяцев**.
- Вариант B: около **7–9 месяцев**, и результат вне экосистемы HL7.

**Где живёт.** Слой XML — новый крейт в fml-rs (`fml-xml`). Карты, корпус, метрики и CLI — новый репозиторий `../ccda-fhir`. В сервере — две операции поверх `Binary`; API остаётся JSON-only, XML бывает только содержимым `Binary.data`. Подробно в разделе 6.

**Почему стоит браться.** Окно совместного существования C-CDA и FHIR закреплено регуляторно. В США HTI-5 (финальная, 2026-10-28) сохраняет приём/отправку C-CDA по (b)(1) до 2030-01-01, а валидацию C-CDA — и после [A6]. В ЕС EHDS требует обмена Patient Summary с марта 2029, и MyHealth@EU переводит свой CDA Patient Summary на FHIR к этому сроку [A6]. Открытого конвертера уровня продукта на FML для US C-CDA нет [B2].

## Как собирались данные

- Пакеты разобраны по tarball'ам с packages.fhir.org, `package-list.json` с hl7.org, CI-манифестам build.fhir.org. Счёт определений — по файлам, а не по документации.
- По GitHub API (2026-11-04) собраны даты коммитов, лицензии, число issue. Счёт шаблонов и строк карт — по shallow-клонам. Чужой код не запускался.
- Локально прочитаны: fml-rs (движок, проверка типов), fhir-test-cases (`structure-mapping`), canonical-manager.
- Помечено **[не проверено]** то, что видно только в поисковой выдаче или на страницах, закрытых для скриптов (Confluence HL7, Research Square).
- Коммерческие FHIR-серверы в документе намеренно не называются. Где они участники консенсуса HL7 или авторы инструментов, они описаны обобщённо.

## 1. Что публикует HL7

### 1.1. Логические модели CDA

| Пакет | Версия, дата | Состав | FHIR | Лицензия |
|---|---|---|---|---|
| `hl7.cda.uv.core` (CDA R2.0) | 2.0.3-sd, 2026-06-12 (informative) | 139 SD (124 logical, 15 примитивов), 26 VS, 2 CS, 15 Schematron | **R5 only** | CC0 |
| `hl7.cda.us.ccda` (шаблоны C-CDA) | 5.0.0, 2026-06-13 (USCDI v6). Ранее 4.0.0 (2025-06), 3.0.0 (2024-05) | 229 SD (Observation 81, Section 66, Act 29, ClinicalDocument 13…), 261 примеров XML | R5 | CC0 |

Как описан XML в `hl7.cda.uv.core` [A1]:
- `xml-namespace` (138 на уровне SD: 133 `urn:hl7-org:v3`, 5 `sdtc`; 91 на уровне элементов, в основном sdtc), `xml-name` (86/69), `logical-container`, `type-profile-style = cda` («профиль применяется через templateId»), `xml-choice-group` (2: `AD.item`, `EN.item`).
- `representation`: xmlAttr ×251, typeAttr ×12, xmlText ×4, cdaText ×1 (`Section.text`, XHTML).
- `xsi:type` выражен через typeAttr на многотипном элементе: у `Observation.value` 29 допустимых типов. Тип по умолчанию задаёт `elementdefinition-defaulttype`, например `SubstanceAdministration.effectiveTime` → SXCM-TS.
- В IG есть своя функция FHIRPath `hasTemplateIdOf()`.

Важные оговорки:
- **R4-сборок моделей нет.** Модели R5, а C-CDA on FHIR и US Core 6.1 — R4. Значит, карты должны смешивать определения разных релизов. fml-rs это уже умеет для кросс-версионных карт: версия входит в URL.
- **В ходу два канонических URL.** Старый `http://hl7.org/fhir/cda/StructureDefinition/*` (пакет `hl7.fhir.cda`) и новый `http://hl7.org/cda/stds/core/StructureDefinition/*`. Часть чужих карт на старом, их переиспользование требует миграции URL.

### 1.2. C-CDA on FHIR (`hl7.fhir.us.ccda`)

- **2.0.0 (STU2), 2026-06-05, R4, зависит от US Core 6.1.0.** Профилей 0: документные профили убраны до следующей версии. ConceptMap 42, все терминологические и статусные: 22 CF (C-CDA→FHIR) и 20 FC (FHIR→C-CDA). 10 XML-примеров. Лицензия CC0 [A2].
- **Таблицы соответствий** — HTML и Markdown, пути CDA похожи на XPath. Исполняемых StructureMap/FML нет ни в одном релизе.

| Домен | CF (строк, ~) | FC (строк, ~) |
|---|---|---|
| Patient | 26 | 15 |
| Participations | 15 | — |
| Allergies | 17 | 15 |
| Encounters | 15 | заглушка |
| Immunizations | 21 | 22 |
| Medications | 35 | 22 |
| Notes | 11 | заглушка |
| Problems | 18 | 12 |
| Procedures | 14 | 12 |
| Results | 36 | заглушка |
| Social History | 26 | заглушка |
| Vital Signs | 22 | 17 |

- **Зрелость.**
  - CF согласованы несколькими вендорами (семь компаний и VA) на Connectathon'ах [A2].
  - FC «пилотировала одна компания… без мультивендорного консенсуса и тестирования на Connectathon» [A2].
  - Известные проблемы: MedicationActivity → MedicationRequest, асимметрия nullFlavor, автор → Provenance [A2].
- **Следующая версия 2.1.0** (ветка `fsh`, CI 2026-11-02, январский баллот 2027):
  - 12 YAML-файлов «correspondence» (путь CDA, путь FHIR, трансформация), которые сверяются с примерами при сборке;
  - таблица покрытия USCDI: 138 элементов, 80 сопоставлены, 28 запланированы;
  - упомянутый черновик StructureMap с пилотом только по аллергиям (~60 строк FML, informative) [A2].

### 1.3. Карты FML/StructureMap для CDA

- **Официального набора карт CDA⇄FHIR у HL7 нет** [A3].
- В fhir-test-cases 4 CDA-теста `structure-mapping`, и все они направления **QuestionnaireResponse JSON → CDA XML** по тестовой модели `urn:hl7-org:v3-test`. Теста с CDA XML на входе нет. Файлы не менялись с 2022-05 [A3]; локальная копия это подтверждает.
- Сообщество:

| Проект | Направление | Объём, охват | Модель | Лицензия | Активность |
|---|---|---|---|---|---|
| HL7 Switzerland `hl7ch/cda-fhir-maps` | оба (отдельная карта на каждое) | 19 карт, 3 782 строки: типы данных, generic Bundle↔CDA, CH-EMED | старый URL в пакете 0.3.0 | Apache-2.0 | 2025-01 |
| HL7 Austria `CDA2FHIR` | CDA→FHIR R4 | 4 карты, 12 835 строк: ELGA Lab и e-Vac, ветка MyHealth@EU LRR | новый URL | **нет LICENSE** | 2026-10 |
| HL7 Italy `cda2fhir` | CDA→FHIR R4 | 11 StructureMap (9 типов документов), для национального шлюза | старый URL | CC0 | 2026-10 |
| TermX (Эстония) `cda2fhir` | CDA→FHIR **R5** | 26 карт, 3 типа документов | новый URL | MIT | 2024-12 |
| ANS (Франция) mapping IG | CDA→FHIR R4 | PoC; «не проверено на реальных данных» | — | MIT | 2026-07 |

Выводы:
- FML для CDA реально используется в Европе для **национальных** CDA, но не для US C-CDA широкого охвата [B2].
- Карты длинные: у Австрии ~12,8 тыс. строк на два типа документов.
- Двунаправленность везде устроена как две отдельные карты [B5].
- Исправления в эталонном Java-движке за 2023–2025 касались именно XML-слоя: xsi:type у ST/CS, сериализация choice-group, разбор дат, `ST.r2b`, «null» в частях адреса. Логики карт они не касались [B4].

## 2. Открытые конвертеры: что есть и чем болеют

| Инструмент | Подход | Направление | FHIR | Состояние |
|---|---|---|---|---|
| microsoft/FHIR-Converter (MIT) | Liquid, 822 файла шаблонов | только C→F | R4 | шаблоны C-CDA заморожены с 2022-04; нет Plan of Treatment, Assessment, A&P |
| Порт на Python (python-fhir-converter) | те же шаблоны | C→F | R4 | спит с 2024 |
| NurraHealth/ccda-to-fhir (MIT, Python) | ручной код, Pydantic, «падать громко» | C→F | **R4B** | молодой, активный |
| alvinhenrick/ccda2fhir (MIT, Rust) | ручной код, отчёт о потерях | C→F | R4, US Core 6.1 | создан 2026-10-24 |
| Google healthcare-data-harmonization (Whistle v1) | DSL, вход — CDA, уже переведённый в JSON | C→F | R4 | конфиги не меняются с 2023 |
| eCR XSLT (eICR/RR) | XSLT 2/3 | оба | R4 (XML) | только public health |
| srdc/cda2fhir, amida (Java, MDHT) | ручной код | C→F | DSTU2/R4 | заброшены; MDHT в архиве |
| TS-библиотека открытого FHIR-сервера одного вендора | ручной код | оба | R4 | активна; единственный открытый общий F→C |

**Типовые дефекты** — их надо сделать первоклассными примитивами в любом варианте [B3]:
1. Точность и часовой пояс TS: дополнение до 1 января, UTC вместо локального времени, отклонённое `+00`.
2. Разные формы IVL_TS (low/high, value, width), а значит потерянные даты.
3. Маршрутизация по одному `templateId[0]`: секция с «entries optional» первым id молча теряется. Секции Plan, Assessment и A&P не сопоставлены вовсе.
4. Ссылки на нарратив (`originalText/reference`, ED): либо выпадают, либо подставляются как текст.
5. REAL, диапазоны доз и единицы PQ.
6. moodCode и статусы: план превращается в заказ; статусы Condition и Medication теряются.
7. Семантика секции: история семьи превращается в наблюдения самого пациента.
8. Идентичность и дедупликация: хеш-id против `ifNoneExist`; автор → Provenance не реализован ни у кого, HL7 сам пишет, что «реализаций для проверки нет».
9. Выход не проходит валидацию (в препринте 257 из 330 AllergyIntolerance невалидны).
10. Сходится практика «падать громко + отчёт о пропущенном»: неизвестные шаблоны — ошибка или явная запись в отчёте.

**FHIR → C-CDA незрел везде.** У HL7 7 доменов FC от одного вендора, у Microsoft этого направления нет, общий открытый генератор один [B5].

## 3. Вариант A: fml-rs + логические модели CDA + XML

### 3.1. Что нужно сделать

| # | Работа | Где | Оценка |
|---|---|---|---|
| A1 | **XML → дерево движка по логической модели.** Пространства имён, xmlAttr/xmlText, typeAttr (`xsi:type` + defaulttype), choice-group, sdtc, `Section.text` как неразобранный XHTML. Позиции узлов для трассировки | новый крейт `fml-xml` | 2 нед |
| A2 | **Дерево → XML.** Порядок элементов по определению, атрибуты против элементов, вывод `xsi:type`, префиксы, нарратив | `fml-xml` | 1,5 нед |
| A3 | **Логические модели в проверке типов и движке:** пакеты R5 рядом с картами R4, `type-profile-style = cda` (выбор группы по templateId), FHIRPath `hasTemplateIdOf()` | fml-check, fml-engine, fhirpath-rs | 1–1,5 нед |
| A4 | **Общие карты типов данных** в обе стороны: II↔Identifier (OID↔URI через NamingSystem из `hl7.terminology`), CD/CE↔CodeableConcept, TS↔dateTime с точностью и зоной, IVL_TS↔Period, PQ↔Quantity (UCUM), AD/PN/TEL, ED и ссылки на нарратив, nullFlavor↔dataAbsentReason | `ccda-fhir` | 2–3 нед |
| A5 | **CDA→FHIR R4:** заголовок + 12 доменов CF, ConceptMap CF-* из IG (CC0) | `ccda-fhir` | 6–8 нед |
| A6 | **FHIR→CDA:** 7 доменов FC, остальное — отдельными картами по тем же таблицам в обратную сторону | `ccda-fhir` | 5–7 нед |
| A7 | **Стенд и метрики** (раздел 5), CLI, CI | `ccda-fhir` | 2–3 нед |
| A8 | **Сервер:** две операции, профили выхода, ограничения размера | server-rs | 1 нед |

MVP: A1–A4, A5 для заголовка и 7 доменов (Allergies, Problems, Medications, Immunizations, Results, Vital Signs, Procedures), A7 и A8 только для CDA→FHIR. Итого около 2,5–3 месяцев.

### 3.2. Сильные стороны

- **Совместимость с HL7.** Карты в FML обмениваются и рецензируются в формате, который HL7 рассматривает для 2.1.0. Пилот HL7 по аллергиям можно взять тестом, а свои карты отдать в сообщество.
- **Общий фундамент.** Проверка типов fml-check ловит ошибки путей и типов в картах до запуска. На US Core и xver это уже работает.
- **Трассировка.** `$transform?debug` из коробки: видно, какое правило дало какой элемент. Это прямой ответ на «откуда это поле» и основа отчёта о потерях.
- **Переиспользование.** `fml-xml` пригодится и для других логических моделей (HL7 v2-XML, национальные CDA).
- **Валидация CDA без Schematron-движка.** Шаблоны C-CDA — это StructureDefinition, значит прочитанный CDA можно валидировать нашим fhirschema как логическую модель. **Гипотеза**, проверить на 20–30 примерах до старта A7.

### 3.3. Слабые стороны и как их закрыть

- **FML однонаправлен.** Закрываем дисциплиной: парные карты `X.cda2fhir.map` / `X.fhir2cda.map`, общие карты типов, round-trip-тест на каждый домен в CI. Плюс «correspondence»-таблицы в формате ветки `fsh` HL7 как оракул тестов, а не как язык.
- **Карты многословны.** Объём сокращают общие группы типов данных и правила по умолчанию `<<types>>`. Ориентир по объёму: швейцарские 3,8 тыс. строк на два направления eMedication.
- **XML-слой хрупок** (опыт эталонного движка). Закрываем фаззингом на корпусе и узлами с позициями: ошибка указывает строку XML.

## 4. Вариант B: свой DSL

Например, «линзы»: одно объявление соответствия `cda.path <-> fhir.path` с парой преобразований, из которого выводятся оба направления.

| Критерий | A: FML | B: свой DSL |
|---|---|---|
| Выразительность | полная: группы, условия, `translate`, `evaluate` FHIRPath, зависимые группы, `produced`-ресурсы; не хватает только удобств | под CDA удобнее (templateId, nullFlavor), но всё нестандартное (Provenance, дедупликация, нарратив) упирается в «escape hatch» к коду |
| Обратимость | парные карты + round-trip-тест | автоматическая только для биективных частей; потерь без указания нет, потому что 1:1 всего немного |
| Тестируемость | трасса движка, проверка типов, корпус; карты HL7 и сообщества — внешний эталон | всё своё; внешнего эталона нет |
| Экосистема | формат HL7; карты читают и правят другие | никто, кроме нас, не знает языка |
| Объём до первой полезной карты | ~4–5 нед (A1–A3) | ~8–10 нед (язык, парсер, проверка, движок, инвертор) + тот же XML-слой |
| Полный объём | ~5–6 мес | ~7–9 мес |
| Риск | XML-слой; R5-модели против R4-цели | дизайн языка, документация и поддержка навсегда; разрыв с направлением HL7 |

**Вывод.** B выигрывает только в краткости объявлений для простых полей. Эту краткость можно получить в A генератором FML из таблиц соответствий, если она понадобится. Обратное не работает: из своего DSL совместимость с HL7 не получить.

## 5. Корпус и метрики

**Корпус в репозитории** (лицензии позволяют): HL7/C-CDA-Examples (447), HL7/CDA-Examples (137), ONC CC0-наборы (162). Нелицензированные наборы (ONC USCDI 276, chb 747) прогоняются только локально, отчёт публикуется без файлов.

**Метрики, на каждый прогон в CI:**
1. **Покрытие секций и entry.**
   - Секция или entry опознаётся по любому из её templateId, а не по первому.
   - Доля entry, ставших ресурсом, по шаблонам и в целом.
   - Список неизвестных шаблонов с частотой.
2. **Валидность выхода.**
   - FHIR: % ресурсов, валидных по US Core 6.1.0, нашим валидатором.
   - CDA: % документов, валидных по профилям `hl7.cda.us.ccda`.
3. **Round-trip.**
   - CDA→FHIR→CDA: доля значимых значений, сохранённых после нормализации (коды, даты с точностью, количества, ссылки).
   - FHIR→CDA→FHIR — то же для примеров US Core.
4. **Явные потери.** Отчёт по каждому документу: что не сопоставлено и почему (по правилу «падать громко»).
5. **Сверка с консенсусом HL7.** Примеры CF/FC из IG и `HL7/ccda-on-fhir/mappings/examples` (158 файлов вывода разных вендоров по одному входу) — проверка «как у большинства».

Публичная цифра для анонса: «N% entry из HL7 C-CDA-Examples → валидный US Core; M% round-trip».

## 6. Где живёт и как подключается

- **fml-rs:** новый крейт `fml-xml` — общий, без знания CDA; `fml run` принимает и отдаёт XML по логической модели. Это пункт «XML input for CDA maps», уже стоящий в плане fml-rs.
- **Новый репозиторий `../ccda-fhir`** (org octofhir):
  - карты по доменам в обе стороны;
  - ConceptMap из C-CDA on FHIR (CC0, с указанием источника);
  - корпус, стенд метрик;
  - CLI `ccda-fhir to-fhir|to-cda|check|coverage`;
  - зависит от fml-rs, модели CDA подтягивает из реестра пакетов через canonical-manager.
- **server-rs:**
  - `POST /fhir/$ccda-to-fhir`: вход `Parameters` с `Binary` (`contentType: application/xml`, `data` в base64), выход — document Bundle и отчёт о потерях в `OperationOutcome`;
  - `POST /fhir/$fhir-to-ccda`: вход Bundle или Composition, выход `Binary` с CDA;
  - стандартный `$convert` не перегружаем: он про форматы и версии FHIR;
  - XML не появляется ни в одном FHIR-эндпоинте, только как содержимое Binary.
- **Консоль:** страница FML уже есть; добавить загрузку CDA-файла и трассу правил.

## 7. Риски

1. **Модели только R5**, цель R4. fml-rs уже держит разные релизы в одной карте; проверить на A3 первой же картой.
2. **FHIR→CDA без консенсуса HL7.** Заявлять как «по таблицам FC HL7 2.0.0, без мультивендорной проверки» и держать отдельной метрикой.
3. **Быстрые версии C-CDA** (3.0 → 4.0 → 5.0 за два года). Целиться в R2.1 + Companion Guide R2 (база таблиц IG), шаблоны 3.0+ поддерживать опознанием по templateId.
4. **Нарратив и Provenance** — открытые вопросы у самого HL7. На старте: нарратив переносим как есть (`Composition.section.text`), Provenance — по таблице IG, помечено «trial».
5. **Чужие карты без лицензии** (HL7 Austria) — только читать как идеи, не копировать.
